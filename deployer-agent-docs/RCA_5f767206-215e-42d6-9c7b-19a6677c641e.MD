# RCA — essenceinvest.com / www.essenceinvest.com returning HTTP 403 "error code: 1014"

## Problem statement
After the user replaced their 4 apex A-records with DNS-only (grey-cloud) CNAMEs
(`@` → `finance-platform-v2.emergent.host`, `www` → `finance-platform-v2.emergent.host`),
both `https://essenceinvest.com` and `https://www.essenceinvest.com` return
**HTTP 403, Cloudflare error code 1014 ("CNAME Cross-User Banned")**. Names now resolve to
`104.18.14.241 / 104.18.15.241` (Cloudflare anycast, inherited from the CNAME target).

## Evidence
- `describe_deployment_state`: `frontend_type = cloudflare` → custom domains are attached as
  **Cloudflare-for-SaaS custom hostnames on the platform's Cloudflare zone**; the public app is
  served from a Cloudflare Worker, not from a customer-owned Cloudflare zone.
- `list_domains` — both custom hostnames are **healthy on our side**:
  - apex `essenceinvest.com` → `cf_custom_hostname_id = 939187fd-727d-41c4-8a5e-120219ab555f`,
    `verified = true`, `ssl_status = active`, `ssl_validation_method = http`.
  - `www.essenceinvest.com` → `cf_custom_hostname_id = 64c7b588-3804-42a8-b49c-6122bfc3a14d`,
    `verified = true`, `ssl_status = active`, `ssl_validation_method = http`.
- `check_domain_status`: both `linked = false`, message **"A records do not point to expected IPs"**
  — the user's DNS no longer points to the target the platform expects.

## Root cause
The 1014 ban is a Cloudflare security rule, **not** a problem with our custom-hostname config.
The user pointed a CNAME from their own Cloudflare zone at `finance-platform-v2.emergent.host`,
which is the **app's own Cloudflare-proxied (orange-cloud) vanity hostname living in a DIFFERENT
Cloudflare account (ours)**. Cloudflare refuses to let a proxied/CNAMEd record in one account
resolve into a proxied record owned by another account — that is exactly what error 1014
"CNAME Cross-User Banned" means. The previous RCA's recommended CNAME **target was wrong**:
`finance-platform-v2.emergent.host` is not a valid Cloudflare-for-SaaS CNAME target; it is the
app URL. `check_domain_status` confirms the platform expects the domains to resolve to a specific
set of **A-record IPs**, not a CNAME to the app hostname.

## Re-validation question
**No re-validation is required on our side.** Both custom hostnames are still `verified=true` with
`ssl_status=active`; the DNS edit did not invalidate them. Nothing was changed or needs changing on
the Cloudflare-for-SaaS custom-hostname records (939187fd… / 64c7b588…). The only broken piece is the
customer's own DNS. (Caveat: these use HTTP-01 validation — while DNS returns 1014 the edge cannot
serve the validation token, so a future cert *renewal* could stall; this is not a problem right now
because the certs are already active, and it resolves itself once the DNS points correctly again.)

## Fix
**User (DNS — in their own Cloudflare zone):** Remove the two CNAMEs that point to
`finance-platform-v2.emergent.host` and restore the records the platform expects, exactly as shown in
**Deployment Panel → Domains** for this deployment:
- Recreate the **apex A-records** (`@`) pointing to the expected IPs listed in the Domains tab, set
  **DNS-only (grey cloud)**.
- Point **www** at the same expected target (A-records / the exact target shown in the Domains tab),
  **DNS-only (grey cloud)** — again NOT a CNAME to `finance-platform-v2.emergent.host`.
The grey-cloud (DNS-only) requirement is correct and should be kept; the error was the *target*, not
the proxy setting. Once DNS points to the expected IPs, Cloudflare routes on the Host header to the
already-active custom hostnames and the 403/1014 clears (allow for DNS TTL/propagation).

After the DNS change, re-run `check_domain_status` to confirm both report `linked = true`.
