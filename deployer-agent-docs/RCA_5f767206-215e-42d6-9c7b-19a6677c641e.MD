# RCA — Custom domain essenceinvest.com returns Cloudflare error 1034

## Problem statement
User pointed `essenceinvest.com` and `www.essenceinvest.com` (Cloudflare DNS, proxy OFF / grey-cloud) via A-records to `162.159.142.117` and `172.66.2.113`. Visiting either domain returns Cloudflare **error code 1034 ("Edge IP Restricted")**. User asks whether the domains are registered/verified on this deployment, their SSL status, and whether any extra DNS record (TXT/CNAME) is required.

## What I verified (evidence)
- `describe_deployment_state`: deployment `finance-platform-v2`, active run `5f767206-215e-42d6-9c7b-19a6677c641e` (success), `frontend_type: cloudflare`, live URL `https://finance-platform-v2.emergent.host`. Domains listed: `www.essenceinvest.com` (verified), `essenceinvest.com` (verified).
- `list_domains`:
  - `essenceinvest.com` → `verified: true`, `ssl_status: active`, `ssl_validation_method: http`, provider cloudflare, `root_redirect_enabled: true`.
  - `www.essenceinvest.com` → `verified: true`, `ssl_status: active`, `ssl_validation_method: http`, provider cloudflare, `root_redirect_enabled: true`.
- `check_domain_status`: both domains `linked: true` (live A-record check matches our expected target).
- `preview_health_check` on default URL: HTTP **200**, serves the real app (Fröhlich Vermögensberatung).

## Root cause
Nothing is broken or missing on the Emergent/platform side. Both custom hostnames are registered, **verified**, and have **active SSL** issued via **HTTP validation** — which means **no verification TXT record and no CNAME is required**. The A-records are already recognized (`linked: true`).

The **error 1034 ("Edge IP Restricted")** is generated by the **user's own Cloudflare zone**, not by our edge. It occurs when a Cloudflare zone resolves a hostname to a **Cloudflare anycast IP** (162.159.x / 172.66.x) via grey-cloud A-records while that same hostname is served by a *different* Cloudflare account (ours, via Cloudflare-for-SaaS custom hostnames). Cloudflare's edge sees the record inside the user's zone pointing at a Cloudflare-owned IP it is not authorized to originate for, and refuses it → 1034. This is the classic "customer domain is itself hosted on Cloudflare + grey-cloud A-record to a Cloudflare IP" conflict.

## Required records (exact)
- **No additional TXT record** is needed — SSL is HTTP-validated and already `active`.
- **No CNAME verification record** is needed for ownership.
- The apex + www must route to our SaaS edge **without a two-Cloudflare conflict**. Recommended records on the user's Cloudflare:
  - `essenceinvest.com` → **CNAME** `finance-platform-v2.emergent.host` (use Cloudflare CNAME flattening at the apex), **DNS only (grey cloud)**.
  - `www.essenceinvest.com` → **CNAME** `finance-platform-v2.emergent.host`, **DNS only (grey cloud)**.
  - Remove the 4 grey-cloud A-records to `162.159.142.117` / `172.66.2.113`, which are the source of the 1034.

## Fixes
- **User (domain):** In their Cloudflare dashboard, delete the grey-cloud A-records pointing at the Cloudflare anycast IPs and replace with DNS-only CNAMEs to `finance-platform-v2.emergent.host` for both apex (CNAME flattening) and www. Confirm all records are grey cloud (proxy OFF). Re-test in an incognito window after propagation. No change is required in the Emergent UI — the domains are already added, verified and SSL-active.
- **Platform (if 1034 persists after the CNAME change):** Escalate to Emergent support to confirm the Cloudflare-for-SaaS fallback-origin routing for custom hostname IDs `939187fd-727d-41c4-8a5e-120219ab555f` (apex) and `64c7b588-3804-42a8-b49c-6122bfc3a14d` (www).

## Not the cause
- Not a missing verification record (HTTP validation, SSL already active).
- Not an unverified/pending domain (both `verified: true`).
- Not an app outage (default URL returns 200).
