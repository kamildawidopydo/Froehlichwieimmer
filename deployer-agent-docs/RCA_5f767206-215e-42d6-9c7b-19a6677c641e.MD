# RCA — Custom domain essenceinvest.com / www.essenceinvest.com not serving (1014 / 1034)

## Problem statement
Custom domain `essenceinvest.com` and `www.essenceinvest.com` do not serve. Customer's zone (zone id `d8c7e9e7b2e2e4ec8de12071906fed78`, created 2026-10-23, moved from a prior Cloudflare account with NS grannbo/kip) is itself a full, active Cloudflare zone. Customer tested 4 DNS variants, each 60–90s:
1. A @ → 162.159.142.117 + 172.66.2.113, www CNAME → essenceinvest.com, DNS-only → **error 1034 (Edge IP Restricted)**
2. Same records proxied (orange) → **1034**
3. CNAME @ and www → finance-platform-v2.emergent.host, DNS-only → **error 1014 (CNAME Cross-User Banned)**
4. Same CNAMEs proxied (orange / O2O) → **1014**
Zone currently restored to documented setup (variant 1).

## What is NOT broken
- App is healthy. `preview_health_check` on the default URL `https://finance-platform-v2.emergent.host/` → HTTP 200, real app content (Fröhlich Vermögensberatung finance platform). Default domain serves fine.
- Latest run `5f767206-215e-42d6-9c7b-19a6677c641e` (redeploy) = success. frontend_type = **cloudflare** (static served from R2 via a Cloudflare worker; `/api` proxied to the k8s backend).

## Stored custom-hostname state (from my tools)
`list_domains`:
- essenceinvest.com — verified:true, ssl_status:active, ssl_validation_method:http, root_redirect_enabled:true, cf_custom_hostname_id `939187fd-727d-41c4-8a5e-120219ab555f`
- www.essenceinvest.com — verified:true, ssl_status:active, ssl_validation_method:http, root_redirect_enabled:true, cf_custom_hostname_id `64c7b588-3804-42a8-b49c-6122bfc3a14d`

`check_domain_status`: both `linked:true` (DNS resolves to our edge).

These reflect OUR stored Cloudflare-for-SaaS records only. I have no tool to re-trigger Cloudflare real-time validation, recreate a custom hostname, inspect worker-route / fallback-origin coverage, or enable O2O.

## Root cause
Edge-level Cloudflare-for-SaaS routing authorization for this customer zone is not functioning, even though the custom-hostname records report verified + SSL active:
- **1014** (variants 3 & 4): cross-account CNAME into the SaaS zone is reaching the edge but the custom-hostname / cross-user authorization is not honored.
- **1034** (variants 1 & 2): Cloudflare anycast edge IPs are not authorizing this hostname for O2O.

Both codes, persisting across every documented DNS variant, indicate the blocker is on the Emergent-side Cloudflare-for-SaaS configuration (likely stale O2O / custom-hostname edge state after the customer zone was moved between Cloudflare accounts), not the customer's DNS. Customer DNS has already been exhaustively tested.

## Fix / handoff
This requires Emergent platform/Cloudflare-for-SaaS admin action — outside the deployer agent's tools:
1. Re-validate / recreate the two custom hostnames (`939187fd-…` apex, `64c7b588-…` www) to force fresh real-time validation after the zone move.
2. Confirm/enable O2O (orange-to-orange) authorization for the customer zone, and confirm the worker route + fallback origin cover `essenceinvest.com` and `www.essenceinvest.com`.
3. After O2O is enabled server-side, the working customer-side config is the O2O variant: a **proxied (orange-cloud) CNAME** for apex (CNAME flattening) and www → `finance-platform-v2.emergent.host`. Until O2O is authorized on our side, no customer-side DNS variant will resolve the 1014/1034.
